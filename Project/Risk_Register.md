# Risk Register

| ID | Risk Description | Possible Cause | Probability | Impact | Mitigation / Response Strategy |
|---|---|---|---|---|---|
| R1 | Requirements for B2B or partner module change or remain unclear, forcing rework late in the project; the project goes out of scope. | The vendor relationship management and corporate accounts are the least familiar part for the team as it's exploring a new domain. Additionally, no real client (an airline) is available to confirm our expectations or help the team with requirements elicitation, which can affect the feasibility analysis. | High | Medium | Since this project is a gradual learning experience for the team, we can schedule B2B work in Increment 4, after we have learned from the previous increments. We must also agree on a written definition of a corporate account and a partner record before implementing it (coding). |
| R2 | Free-tier hosting and database limits might be exceeded which can block development or testing. | Neon free tier provides 0.5 GB storage and Render gives 750 free instance hours per workspace per month with 1GB storage free for 30 days. If we implement the idea (go beyond the design phase of the project) generated test data and repeated deployments consume both. | Medium | Medium | We can test locally by default and deploy only for demonstrations and milestones. We must monitor the limits strictly. In case limits are reached, we fall back to a local PostgreSQL instance, which might not require any code change, making the transition smooth and easier if needed. |
| R3 | Team member is unavailable around the deadline and his module/task is not finished. | The member might be ill, or might have many submissions/exams from other courses | Medium | High | We can assign a primary and secondary owner for each increment. Furthermore, we can push to the remote repository on a weekly basis so work is saved along with a short description so other members can continue. So if someone falls behind, work can be allocated to someone else. |
| R4 | Integrating a new increment breaks features delivered in an earlier increment | Each increment merges into a growing system; modules share the customer and account schema, so a schema change can affect delivered code | Medium | High | For smooth process, we must agree on module interfaces in writing before the parallel work starts. Furthermore, merge feature branches into master only when the build and test pass successfully. We can also tag a working release at the end of each increment, so a stable version exists and we don't lose the latest best version. |
| R5 | The system behaves correctly on mock data but would not hold up against real airline data | The team does not have access to a live GDS (Global Distribution System for Airlines) or an existing reservation system of an airline; booking data is populated by simulated import as is recorded in the out-of-scope list | Medium | Medium | Model the mock import on realistic booking record fields and volumes rather than convenient values. Include many cases such as cancellations, multi-leg trips, duplicate passenger records and missing contact details. State the assumption explicitly in the requirements and design documents. |
| R6 | Customer's personal data can be exposed because of insecure storage or weak access control. | The CRM would store names, contact details, travel history and complaints. Access is shared across several staff roles. If an account is given more permissions than it needs, personal data can be exposed. | Medium | High | We must enforce role-based access on the server side and not only on the interface. Credentials should be hashed, sensitive actions should be restricted to specific roles, and access to customer records have to be logged. We aim to use fabricated data for all testing and demonstrations. |

As stated in the aforementioned table, the risks are expected to be reviewed at the end of each increment (or can be reviewed weekly). Risks R3, R4 and R6 carry the highest impact and are checked at every merge to main branch/increment. As stated above, R1 is reassessed before Increment 4 begins.

Any risk that takes place is expected to be recorded together with the response taken by the team, so the register reflects the project as it develops.
