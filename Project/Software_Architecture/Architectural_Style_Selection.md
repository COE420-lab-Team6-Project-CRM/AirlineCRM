# Architectural Style Selection

We chose a closed 3-layer architecture, which is a special case of the layered style. The application layer is divided into four partitions, one for each business area.

**Main characteristics:** The system has three ordered layers. The presentation layer is the React web UI in the browser. The application layer, or middleware, is the Node.js server. The data layer is PostgreSQL locally and Neon when deployed. The architecture is closed, so each layer calls only the layer directly below it and the UI never reaches the database. The application layer has four partitions: Customer Service, Loyalty and Relationships, Marketing and Reporting, and Access Control. Partitions in the same layer may use each other’s services.

**Why it fits AirlineCRM:** The Feasibility Study already fixes a web stack: React on Vercel, Node.js on Render, and PostgreSQL on pgAdmin or Neon. These three deployment units map directly onto the three layers, which is the web example the lecture gives for this style. Almost every use case is a staff member filling in a form or looking up shared customer data. Requests therefore follow one path, from the UI to the business rules to the database.

**Support for the design goals:** For security (DG-01), every request passes through the application layer. There, Access Control runs StaffAccount.authorize() and records denied attempts in AuditLogEntry before any data is touched. The browser holds no database credentials, and encryption at rest (NFR-02) is handled once, in the data layer. For maintainability (DG-02), the UI, the business rules and the database can change independently. The partitions follow the three areas pewviously modeled: customer and service operations; loyalty, feedback and business accounts; and marketing, communications, access and reporting. Moving from local PostgreSQL to Neon changes only the data layer’s connection settings (NFR-15). Performance (DG-03) is only partly supported, because closed layers add one call per request. Search and aggregation queries run inside the data layer, close to the database, so the extra hop is small compared with the 2 to 5 second limits.

**Advantages.** Coupling between layers is low, since each layer knows only the one below it. A layer can be replaced; for example, a future mobile app could reuse the same application and data layers. Each layer can also be tested and deployed on its own, which matches our free-tier hosting plan.

**Limitations.** Runtime efficiency is lower than in an open architecture, because even simple read-only views such as UC-04 pass through every layer. The application layer can grow large, so its partitions must keep their interfaces small to avoid tight coupling. The single data layer is also a shared point of failure, which means NFR-09 rollback has to be handled there.

**Alternatives considered.** Client/Server fits the request-and-response pattern, but it puts the business rules and data access in one server, which weakens DG-02 and NFR-15. A Repository style would let the subsystems share customer data, but they would all depend on one data model. There would also be no single place to check permissions before a write, which works against DG-01. MVC suits showing several views of the same data, which our forms rarely need, and it adds components without helping security.
